What a Skill actually is

A Skill is not a plugin, a fine-tuned model, or anything that requires a developer. It is a single Markdown file that lives in a named folder. The file tells Claude two things: when to use this set of instructions, and what to do when it does. That is the entire structure.

The difference in practice is significant. Without a Skill, you explain your format every time you open a new conversation. With one, Claude already knows. Paste your raw material, get your structured output, no preamble required.

The core idea

Write your instructions once, the way you would brief a new hire. Claude reads the file and applies it consistently, every single session, without you re-explaining yourself.

How to build one in 90 seconds

  1. Name your folder after the job it does. Something like meeting-notes or weekly-report. The name is just for your own navigation, not something Claude reads.
  2. Create a file inside it called SKILL.md. That filename is what Claude recognises. Capitalisation matters.
  3. Write one trigger line at the top. Example: "Use this when I paste a meeting transcript." One sentence is enough. It tells Claude when to activate the Skill rather than behaving generically.
  4. Add your instructions below it. Write them the way you would explain the task to someone on their first day. Be specific about the output format, what to look for, and anything you always want flagged. Three to five sentences covers most jobs.
  5. Drop the folder into Claude's designated Skills directory. Claude picks it up without any restart. Open a new conversation and paste your raw material.

A real example: meeting-notes

Here is the Skill file used for turning messy transcripts into structured notes. The entire file is below, and the instructions are three sentences:

SKILL.md · meeting-notes
Use this when I paste a meeting transcript.

Pull out every decision, the owner responsible for it, and the
deadline if one was mentioned. Present the results as a table
with three columns: Decision, Owner, Deadline. If any decision
has no owner listed, flag it in a separate row marked
"Unassigned" so nothing slips through without accountability.

The result, after pasting a 40-minute transcript: a table built automatically, three decisions listed, one flagged as unassigned because nobody claimed it in the meeting. No format negotiation, no follow-up prompt asking Claude to restructure the output.

Same Skill, same output structure, every time.

Skills worth building for common jobs

If you repeat a task more than a few times a week and you always want the same output shape, it is a candidate for a Skill. A few patterns that translate well:

TranscriptsExtract decisions, actions, owners, and deadlines. Flag anything unassigned.
Client emailsSummarise the request, the tone, and any implicit deadline in three bullet points before drafting a reply.
Research dumpsPull out the three most relevant points for a specific audience, cite the source line, discard everything else.
Weekly reportsRestructure raw notes into a fixed template: wins, blockers, next steps, one number that matters.
Feedback reviewGroup comments by theme, note sentiment, surface the one thing that comes up most often.

Writing instructions that actually work

The quality of the output is almost entirely determined by the specificity of the instructions. A few things that consistently make Skills more reliable:

  • Name the output format explicitly. "Put it in a table" beats "organise it clearly." Claude follows format instructions precisely when they are precise.
  • Tell it what to do with the exception, not just the standard case. The meeting-notes Skill is useful because it handles the unassigned case. Skills that only describe the happy path produce inconsistent output when the happy path does not appear.
  • Write at the level of a capable new hire, not a machine. Avoid jargon that only makes sense inside your head. If the instruction would confuse a smart person reading it for the first time, it will produce inconsistent results.
  • Keep it short. Three to six sentences covers almost every recurring task. Longer files do not produce better output and are harder to maintain.

The honest bit

  • Skills do not replace judgment on genuinely complex or novel tasks. They are for things you already know how to do that you want to stop explaining repeatedly.
  • The trigger line matters. If it is too vague, Claude may apply the Skill when you do not want it. Be specific about the input type, not just the job type.
  • You will probably revise the instructions after the first real use. The first version is rarely the final version. Run it on a real piece of work before considering it finished.
  • Skills work because the instructions are stored, not because Claude learns permanently. If you change how you want the output structured, update the file. Claude reads it fresh each session.
